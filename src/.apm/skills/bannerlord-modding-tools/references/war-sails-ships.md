# DADG War Sails ship authoring in the native editor

Use this reference for the DADG cog, carrack, and English boat conversion. The current status is in `../../DellarteDellaGuerraMap/HANDOFF.md` relative to Core `src`; read it before continuing. All ship sources, tools, drafts and audit evidence live in Map `Tools/WarSailsShips/`. Package paths below are relative to Core `src`. ## Launch and asset discovery

- In Rider, use `DellarteDellaGuerra.Integration: Standalone.Editor.WarSails`, defined by `DellarteDellaGuerra.Integration/Properties/launchSettings.json`. It targets `bin/Win64_Shipping_wEditor/Bannerlord.exe` and loads `NavalDLC` before all DADG modules, including Map and Scenes. Verify the actual running editor and loaded Map module before editing; a selected Rider configuration alone does not establish this.
- Preserve unsaved editor work before a restart. Loose Map `NestedPrefabs/<name>/<name>.xml` files need the editor's `<prefab_definition>` root around the nested `<entity>`. Restart/rescan the editor after external loose-file edits. In the restarted Map editor, the **Prefabs** browser with **All Modules / All Files** and `dadg_ws` filter showed all three visual ship prefabs and six cog/carrack sail candidates with thumbnails. Recheck the browser and warnings for each future edit; the thumbnails establish discovery, not full gameplay setup.
- Keep the loose nested prefab files in Map's `NestedPrefabs`. The packed NavalDLC prefab file and Map's flat `Prefabs` XML use different schemas; neither establishes a requirement to hand-write a packed index for loose authoring.
- When the editor is covered by a launcher, loading window, or dialog, rediscover and capture the actual `Win64_Shipping_wEditor` window using the parent skill's computer-use procedure. Do not infer readiness from a process name or stale window handle. Entering **Edit Mode** took about ten seconds after one click in this session; wait for the transition, then rediscover the new `Edit Mode` window handle and title. Double-clicking its title bar maximized the editor. A direct launcher failure such as “There is no target file” is not evidence that the Rider editor profile failed.

## Source import and validation

- Retain the original Scenes models. Edit only copied DADG source FBXs/Blender files under Map, including its `Tools/WarSailsShips` authoring package. Canonical material names belong in the source FBX; a `SecondMaterialGuid` override does not prove the primary material imported correctly. Reimport an existing Resource Browser geometry entry from its mapped `AssetSources` file instead of creating a duplicate with **Import New**. Preserve its import settings and identity.
- Never hand-edit TPAC or `RuntimeDataCache` files. The editor writes them from source. Check each imported metamesh's names, surface bounds and primary material GUID with the package's TPAC audit and `verify_import.py --require-primary`; inspect collision faces and `wood_ship` directly in the native Body Editor. These checks establish imported assets, not working ship physics.
- For separate v3 sails, use the native matching skeleton hierarchy, not extra helper bones. The source has 200 deforming samples at frames 0–199; the compiled geometry may contain 184 optimized morph keys spanning that interval. Audit compiled rig identity and timing before judging animation from key count. For a fresh import, turn **Skeletal Animations** off when only geometry and morphs are needed. Reimporting an existing entry can retain obsolete skeletons and scene animations; clean that entry through the editor after a backed-up identity audit rather than treating a corrected source FBX as proof that duplicates disappeared.

The changed-file popup processed only three of six changed sail sources in this session. Check every expected package after accepting it; use the existing geometry entry's **Reimport** command for any unchanged binding. All six eventually resolved to the Map sail material. Compare asset identities, primary material GUIDs, bounds, counts and flags against the pre-edit audit. These metadata checks do not verify bone topology or morph samples; inspect the compiled payload when those properties need verification.

### Material Editor crash checkpoint

On 2026-09-29, assigning a copied Map texture to `dadg_ws_carrack_window` caused three native editor access violations at the same `TaleWorlds.Native.dll` offset `0x907ca8`. The third occurred in the full Material Editor launched through `TaleWorlds.MountAndBlade.Launcher.exe`; switching editor view or executable did not avoid the fault. The second editor's RGL error log had no exception, but Windows Application Event 1000 recorded it. Inspect both sources when an editor vanishes. All three attempts ended before Save; at that checkpoint the Map material still referenced Scenes textures. The later repair below saved all three Map bindings.

The copied material's exposed shader, flags, layout, blend and scalar settings match both the Scenes original and a successfully edited Map `sho_rope` material. Before the rename test, its three Map textures had runtime data almost byte-identical to the Scenes originals. Read-only native disassembly places the fault at an unchecked dereference of a typed-name resource lookup result, before slot write and diffuse-name auto-completion. The lookup compares name bytes case-sensitively. The two crash-tested carrack texture names are the only mixed-case names among 22 copied textures; a casing or registration mismatch is the leading hypothesis, **not confirmed** by a register capture.

Test that hypothesis with one native change: rename the existing Map BaseColor texture to the same-length lowercase `dadg_ws_window_low_carrack_window_basecolor` in the Resource Browser, verify its GUID/import settings/source/payload remain intact, then assign it to the same DiffuseMap slot of the same material. Do not change compression, material parameters, or name length in the same test. A successful selection supports a name/registration issue but cannot distinguish case from registry refresh caused by the rename. If it fails, stop retrying the picker and capture the lookup key/result at the native breakpoints in `../../DellarteDellaGuerraMap/Tools/WarSailsShips/material-dependency-audit/carrack-native-fault-diagnosis-2026-09-29.md`. Keep the material pending until its saved slots and a clean restart are audited.

Current test status: a direct case-only Rename was ignored; native `..._rename_tmp` followed by the final lowercase name persisted the same texture GUID, import settings, and PNG bytes. Native Rename changed the serialized source path and removed the RDC empirically associated with the earlier package. TPAC byte 8 is package identity, not itself a direct RDC pointer. Context-menu Reimport and Texture Inspector Save did not restore that RDC; the thumbnail went blank and the log explicitly reported missing Map texture pixel data. On War Sails editor startup, the RDC regenerated with the **same hash as before Rename**. Assigning the lowercase texture to the same material's DiffuseMap then succeeded, and native Save persisted its Map GUID in slot 0 while all other material settings remained unchanged. The Map normal texture received the same temporary-name hop, native Save, and restart; its RDC likewise regenerated with its original hash. Normal and specular Map assignments then succeeded in the current editor process. Native Save persisted all three Map texture GUIDs; a disk audit verified the original shader, flags, layout, blend, alpha, and scalar/vector settings were retained. The full Material Editor rendered the saved wood/window material without a fault. This supports a name/registration repair path, but the rename and restart also refreshed registration, so casing alone is not proved. PID 71572 earlier logged a native null-pointer assertion while finalizing the editor screen, and the next launch showed Safe Mode; the prompt's exact trigger was not proved. A fresh whole-editor restart after the final bindings, compiled mesh rebind, and runtime validation remain separate checks. See `../../DellarteDellaGuerraMap/Tools/WarSailsShips/material-dependency-audit/carrack-window-editor-crash-2026-09-29.md` for exact hashes and checks.

### Preserve geometry while renaming FBX materials

Back up copied FBXs and matching Blender sources before changing material names. A structured FBX edit can change only the Material-name property while preserving other node/property bytes; raw string replacement is unsafe because a longer name changes binary record lengths and offsets. Verify the parsed structure before and after, allowing only the intended name and required serialization offsets/alignment to differ. Keep object IDs, geometry, UVs, bones, morph data and animation curves unchanged. Independently import the edited FBX and verify the matching Blender source after save/reload.

Check unused Blender datablocks as well as visible objects: saving the hull sources in this session removed a zero-user legacy material. Preserve required reference data before saving and compare the reopened source semantically. The authoring batch used a version-aware SDNA `Material.ID.name` edit for the affected copies, verified unchanged decompressed bytes outside those name fields, then loaded each result in Blender. This is a narrowly verified source-file technique, not permission to patch compiled TPACs or a reason to prefer binary edits for ordinary Blender work.

Promote verified source files to the exact Map `AssetSources` paths used by existing geometry entries, then reimport in the editor and check compiled primary material GUIDs and rig/timing again. An offline source audit cannot establish native import success. When an older package retains obsolete skeleton or animation identities, an additive source with unique internal object names permits a fresh import without deleting that package; update only the intended prefab references and verify the new identities. Keep source, native import and runtime evidence separate in the work-package status.

## Fit deck and boarding markers to the copied hull

Use the final detailed collision and candidate deck navmesh in the same ship-root coordinate frame. Track waterline shifts explicitly: the English aisle collision already has its +0.15 m shift baked in, so applying that offset again to its entity would invalidate the measurements. Record source hashes, world positions, parent rotations, child-local positions, nav face IDs and connected components in the geometry handoff; verify generated prefab transforms against that handoff before promoting them.

Measure collision support and headroom at every occupied spawn, steering point and climbing landing. Put boarding pilots inside the tagged ID 1/2 faces and reserve their positions when fitting the other markers. Test pairwise spacing including steering and reserve climbing landing space; named spawn roles alone do not establish crew capacity. The English fitting pass found old fore landings outside the walkable aisle and moved them to a wider connected section.

Check the path between deck and rail separately from endpoint placement. The English pilots had deck support and nav containment, but a floor-height line to the rail crossed the hull wall. A raised polyline cleared the rail; that establishes only geometric centerline clearance. Native rope reach, boarding animation, agent capsule clearance, simultaneous occupancy and motion on a moving ship still require editor/mission verification. Keep such candidates in offline gameplay drafts until those checks are performed. The work package's `verify_english_markers.py` checks the generated world/local transforms, roles, IDs and recorded containment against the measured handoff; it is not a runtime traversal test.
